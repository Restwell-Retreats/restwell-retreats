# Automated accessibility audit — 24 Aug 2026

Part of the "make it perfect" workstream, deliverable 1: run axe-core against
every distinct page template at mobile and desktop widths, fix every
serious/critical violation, and document false positives.

## Method

- Installed `axe-core` (`npm install axe-core --no-save`), served
  `axe.min.js` from a local `python3 -m http.server`, and injected it into
  the Playground instance (port 9402) via Chrome DevTools Protocol
  (`Runtime.evaluate` + a dynamically-created `<script>` tag).
- Ran `axe.run({ exclude: [['#wpadminbar']] })` against every page template
  in scope (home, our-story, the-property, accessibility, pricing,
  how-it-works, who-its-for, whitstable-area-guide, resources,
  optional-care/care, faq, enquire, privacy-policy, terms-and-conditions,
  accessibility-policy, plus a sample blog post) at a mobile viewport
  (390×844) and a desktop viewport, both signed in as admin (with the
  `#wpadminbar` excluded so admin-bar markup — which we don't own — doesn't
  pollute results) and, where practical, signed out.
- Re-ran after each fix to confirm zero serious/critical violations remained
  on the affected page.

## Violations found and fixed

| # | Violation | Page(s) | Fix |
|---|-----------|---------|-----|
| 1 | `color-contrast`: `.site-footer__copyright` at `rgba(255,255,255,0.6)` on `--deep-teal` measured ~4.49:1, just under WCAG AA's 4.5:1 for normal text | All pages (shared footer) | Raised alpha to `0.7` in `assets/css/shared.css` (~5.5:1) |
| 2 | `region`: the skip link sat directly under `<body>` with no landmark, so it wasn't reachable by landmark-based navigation | All pages (shared header) | Wrapped it in `<nav class="skip-links" aria-label="Skip links">` in `header.php` |
| 3 | `aria-allowed-attr` / `aria-required-children` / `listitem`: the FAQ category pills used `role="tablist"` + `aria-selected`, but they behave as a filter (re-render the list below), not a tabpanel-swap — the ARIA tabs pattern requires `role="tab"` children inside `role="tablist"` with corresponding `role="tabpanel"`s, which didn't exist | FAQ page | Removed `role="tablist"` (back to a plain `<ul>`), changed `aria-selected` → `aria-pressed` on the buttons in `template-faq.php` and `assets/js/shared.js` — the correct pattern for a toggle-button filter group |

Also caught and fixed in the same pass (not axe-detected, found by manual
content review while on each page): the FAQ page's cancellation-policy
answer described a different refund schedule (admin fee / partial forfeiture
tiers) than the actual policy generated in
`inc/theme-setup/legal-content.php` and shown on the real Terms &
Conditions page (full refund >30 days / 50% refund 14–30 days / no refund
inside 14 days). Corrected the FAQ copy to match — this was a factual
accuracy bug that happened to surface while accessibility-auditing the same
page, not an axe finding.

## False positives / not actioned

- No axe violations were found that were judged false positives requiring a
  documented override. Everything axe flagged as serious/critical was a
  real, fixable issue (above); anything flagged `minor`/`moderate` that
  didn't represent an actual barrier (e.g. WordPress core admin-bar markup,
  which is excluded from the run entirely) was out of scope by design, not
  suppressed.

## Verification

- Re-ran `axe.run({ exclude: [['#wpadminbar']] })` on every listed template
  at both viewports after the fixes above: 0 serious/critical violations
  remaining.
- Manually confirmed in-browser: skip link still focuses and jumps to
  `#main-content` on Tab; footer copyright text is legible against the teal
  background; FAQ filter pills still filter the list correctly with
  `aria-pressed` reflecting the active pill (verified via CDP snapshot).

## Known limits of this audit

This is an automated axe-core sweep plus manual review, not a substitute
for testing with a screen reader (VoiceOver/NVDA/JAWS) or with real assistive
technology users. Axe-core catches a meaningful chunk of WCAG failures (missing
labels, contrast, ARIA misuse, landmark structure) but not everything —
reading order with a screen reader, actual keyboard-trap behaviour in
carousels/lightboxes under real AT, and cognitive-load/plain-language
concerns all need human testing that wasn't performed here.
